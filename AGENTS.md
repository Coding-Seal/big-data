# Agent instructions

This file is the shared instruction set for any coding agent working in this repo — Claude Code, Codex CLI, opencode, or others. `CLAUDE.md` imports this file verbatim; don't fork Claude-specific instructions into a separate file, add a `## Claude Code notes` section below instead if something is truly tool-specific.

## What this project is

A course project ("polytech big-data"): an extensible pipeline that answers research questions about Wikipedia pageview traffic (topic/time patterns, spikes vs. news, decay after peaks, length/revision correlation, weekday/weekend patterns) using Spark over Wikimedia's public dumps. Grading emphasis is **software engineering quality and extensibility** — answering a new question or adding a data source should mean adding one file, not touching what already works. See `docs/arch/README.md` for the full design rationale and `docs/sources/README.md` for the data sources themselves (one file per source: location, format, size, description).

Using Spark is an intentional assignment constraint ("serious tools, even if overkill"), not a scale requirement — don't suggest replacing it with pandas/dask just because a given data slice is small.

## Repo layout

- `tasks.md` — what's still outstanding, carried between sessions. **Read it first**: it names the next concrete step and flags anything that is implemented but unverified. Update it as work lands. Finished work does not accumulate there — durable facts go to "Known gotchas" below or to `docs/`, the narrative to git history.
- `docs/sources/` — one file per Wikimedia dataset (location, format, size, description). Read the relevant file before integrating a new source, and before assuming any size/format fact about an existing one.
- `docs/arch/` — system architecture, one file per concern (layered design, ingestion/storage). Read `docs/arch/README.md` first; read before changing the pipeline's shape.
- `src/` — the real pipeline, per `docs/arch/layered-design.md`, laid out by stage: `pipeline/` (bronze/silver/gold + Spark bootstrap, chart specs, logging setup), `sources/` (one module per dataset + its download/parse helpers), `questions/` (one module per research question + the shared page/category helpers, registered in `questions/__init__.py`), `run.py` (CLI dispatch only). No `common/` — each helper lives in the one layer that imports it, not a catch-all. `silver.build()` is three separately callable steps so a run that dies partway resumes one step at a time.

  Run via `just download` / `just build-silver` / `just question <name>` (see `justfile`), or `uv run python3 src/run.py <command>` directly. There is no `poc/` anymore — all five questions and all three sources are implemented here; new work always lands in `src/`, never in a new throwaway script.
- `config.yaml` — wiki(s), date range, storage root. Lives at the repo root, not under `src/`, since it's configuration, not code. `config.enwiki.yaml` is a second profile for the same pipeline (`run.py --config <file>`, or `just config=config.enwiki.yaml <recipe>`); Q2 needs it, since simplewiki has no ITN page. Bronze is shared between profiles, silver and gold are per-wiki (`data/silver/<wiki>/...`) — see `run.py::storage_paths`.
- `.agents/skills/` — shared skill docs, one per recurring task: `update-agents-md` and `docs-arch` (maintaining this file and the design docs), `running-pipeline-jobs` (launching, resuming, and diagnosing Spark runs — read before any enwiki run), `validating-question-output` (read before reporting any number a question produced). These are plain conventions any agent should read when doing that kind of work; Claude Code's own skill auto-discovery looks at `.claude/skills/` specifically, so don't assume they're auto-invoked there without also being registered under that path.

## Environment

Python dependency management is **uv** everywhere (`pyproject.toml` / `uv.lock`) — Python is pinned to 3.11: PySpark 3.5.1's bundled `cloudpickle` recurses infinitely serializing closures under newer Pythons (confirmed on 3.14). Don't bump the Python version without re-checking this. Add dependencies with `uv add <package>` (prefixed with `devenv shell --` if using devenv), never hand-edit `uv.lock`.

There are two supported ways to actually run things — pick based on what's available, don't assume one over the other:

- **devenv** — use this on NixOS, or wherever `devenv` is already installed. `devenv shell` provisions JDK 17 + pinned Python 3.11 via nix and runs `uv sync` automatically; prefix commands with `devenv shell -- uv run python3 src/run.py download`. Needs both `languages.python.venv.enable = true` **and** `languages.python.uv.sync.enable = true` in `devenv.nix` — `uv.sync` alone doesn't put the venv on `PATH`, so `python3` silently falls back to the bare nix interpreter and `import pyspark` fails even though sync reported success. First `devenv shell` in a fresh checkout needs network access (flake inputs); later runs are cached.
- **plain uv** — everywhere else. Not automated outside devenv: you need `uv` and a JDK 17 on `PATH`/`JAVA_HOME` yourself (Spark needs a real JVM). `uv sync` fetches the pinned Python 3.11 itself, then `uv run <cmd>`, e.g. `uv run python3 src/run.py download`.

If unsure which applies, check whether a `devenv` binary is on `PATH` (or whether `/etc/os-release` says NixOS) before reaching for `devenv shell --`.

Spark runs `local[*]`, so executors live in the driver JVM and its heap is the entire memory budget. The default (1g) is fine for the `simple` profile and not for `enwiki`'s multi-GB dumps — export `SPARK_DRIVER_MEMORY=6g` for those runs. It has to be an env var: `local[*]` fixes the driver heap when the JVM launches, before `SparkSession.builder.config()` is read, so setting it in code silently does nothing (see `pipeline/spark.py`).

## Conventions

- The silver schema documented in `docs/arch/layered-design.md` is the seam between data sources and research questions. Source modules only ever *produce* silver tables; question modules only ever *read* them — never let a question module reach into bronze or raw dump formats directly.
- Prefer extending the contract (new table) over modifying it (changing an existing table's shape) when adding a source, so existing questions keep working.
- No scheduler, no Delta/Iceberg, no dynamic plugin auto-discovery — these were deliberately rejected as unnecessary for this project's scope (see `docs/arch/layered-design.md`, "Deliberately not doing"). Don't reintroduce them speculatively.

## Known gotchas worth not re-discovering

- MySQL dumps (`page.sql.gz`, `categorylinks.sql.gz`, ...) put `VALUES` on its own line, then one tuple per following line — not the classic single-line extended-insert format. A naive `line.find("VALUES (")` silently parses zero rows, no error; don't fix it with `SparkContext.wholeTextFiles` either, that overflows the driver heap on a 30MB dump. Stream line-by-line, tracking the INSERT block (see `docs/sources/page-dump.md`).
- `categorylinks.sql.gz` does not store category names directly — join through `linktarget` (`cl_target_id` → `lt_id`), filter `cl_type = 'page'` + `lt_namespace = 14`.
- `pagelinks.sql.gz` went through the same `linktarget` migration — `pl_target_id` → `lt_id`, no `pl_title` column. Filter `lt_namespace = 0` for article-to-article links only (otherwise template/category transclusions inflate in-degree). `redirect.sql.gz` was **not** migrated — `rd_title` is still stored directly.
- Raw MediaWiki categories are maintenance/tracking-dominated, not topics — don't treat `category_dim` as a topic taxonomy. Measured: 13/15 of Q1's top categories by views are tracking tags on a sample slice, **15/15** on the full enwiki week (led by `Articles_with_short_description`, 454M views/2.81M articles). `questions/categories.py::is_maintenance` filters by name convention — a heuristic floor; the structural fix is `page_props.sql.gz`'s `__HIDDENCAT__` flag.
- **Category view counts are not additive.** An article carries many categories at once, so a view counts once per category: the enwiki week's top 15 categories sum to ~1.89B against 501.9M of real traffic. Vega-Lite stacks `bar`+`color` by default, so any category chart needs `"stack": None` or it draws ~3.8x reality. Same trap for any future "by topic" breakdown.
- Never group/join `pageviews_fact` by `page_title` directly — `page_dim` is namespace-0 **non-redirect** only, silently dropping redirect traffic (measured 7.2%, concentrated on news-driven pages) and treating each redirect as its own article. Fold through `questions/pages.py::with_page_id` first, aggregate by `page_id`, then join `page_title` back from `page_dim` for display — all five questions do this. The fold also drops titles with no namespace-0 page (`Special:*`, pages newer than the snapshot), so totals are article traffic, not all traffic, and aren't comparable to raw dump counts (enwiki 2026-09-14..20: 6.2% of views arrive under a non-canonical title).
- **`Main_Page` is not dropped by that fold.** It's namespace-0 non-redirect, so `page_dim` keeps it — on the enwiki week it's the single biggest article (32.1M views, 6.4% of traffic) across 15+ title variants that `with_page_id` correctly merges. Front-page traffic has a different weekly rhythm than reading, which is exactly what Q5 measures — decide per question whether to exclude it, don't assume it's gone.
- Averaging over "articles that were viewed" answers a different question than averaging over all articles: ~97% of articles have zero views in a short window, and conditioning on being viewed hid most of Q4's effect (20x → 1.9x). Left-join *from* `page_dim` with a zero fill instead. This is profile-dependent — on a full enwiki week `pct_viewed` is 90.5–99.7% and the two readings nearly agree (71.5x vs 64.9x); the 20x collapse was a simplewiki/short-window artifact.
- **Ranking by absolute peak isn't finding spikes** (Q3's original bug). On the enwiki week, top-10-by-`peak_views` includes `Main_Page` at **1.52x** its own baseline (flat diurnal curve, no decay) while excluding 100–135x pages with smaller absolute peaks (`Indian_Institutes_of_Technology` 122x, `2018` 115x, `Peccary` 107x). Rank by `peak / avg` instead. Most of what survives an absolute-peak ranking at enwiki scale is automated traffic — single-hour impulses at 1.2–4.8% mean-of-peak, for which decay has no referent.
- **Shrinking a join's input can break the job** — not where you'd look for an OOM. Pre-aggregating pageviews to `(page_id, hour)` before the `category_dim` join (`questions/categories.py::views_by_category_hour`, worth ~15%, 29m40s → 25m18s on enwiki) shrank Spark's size estimate enough to switch to a broadcast hash join, which then OOM'd in `BroadcastExchangeExec` on the **simple** profile's 1g heap — where the slower un-aggregated version had just succeeded. The `.hint("merge")` on that join is load-bearing, not tuning: neither side is ever broadcast-sized (183.8M category rows). Expect this whenever an optimization changes cardinality upstream of a big join.
- The `RowBasedKeyValueBatch: ... Will not spill but return 0` warning isn't by itself a sign of bad shuffle config — it also appears on a healthy `shuffle.partitions=200` + AQE run of a 2M-group `countDistinct` (measured 2026-10-28). Check partition count and spill volume, not just the warning.
- Don't raise `spark.shuffle.file.buffer` above its 32k default. At `shuffle.partitions=200`, Spark's `BypassMergeSortShuffleWriter` opens one buffered writer per partition at once — 200 × 1m × 8 concurrent tasks ≈ 1.6GB of raw buffers, enough to OOM the 1g default heap instantly (measured 2026-10-28, died in `BufferedOutputStream.<init>`). The two settings are only dangerous together; partition count alone is fine.
- Silver can hold **more windows than the config asks for**: `partitionOverwriteMode=dynamic` only replaces the `(date, hour)` partitions a write touches, so changing `date_range` and rebuilding leaves the old window on disk. Measured 2026-10-28: `silver/en/pageviews_fact` held both the configured Sept 14–20 and a stale Oct 4–10, so Q2 reported 18/20 spikes as `NEWS_UNKNOWN` and Q5's per-weekday totals silently summed two weeks. `run.py::load_tables` now windows `pageviews_fact` to `date_range` for every question, so this can't recur. The two profiles legitimately configure different weeks, so extra partitions on a shared bronze are normal — don't delete `silver/simple`'s Oct 4–10, that's its actual window.
- Window length is load-bearing for Q2/Q3/Q5, and the failure is silent. With n hourly samples, `views / avg(views)` can't exceed n, so any spike threshold ≥ n returns zero rows by arithmetic — Q2 looked "implemented but finding nothing" on a 2-hour window. Q5 needs at least a full week to have one of every weekday.
- `.gz` pageview files are not splittable in Spark; parallelism comes from file count, not intra-file splits.
- Don't rebuild a timestamp from `pageviews_fact`'s `date`+`hour` — use `ts`. Those two are *partition* columns, so Parquet type-infers them back as ints: `hour=08` → `8`, and `concat(date, hour)` yields `"202610068"`, parseable for hours 10–23 but throwing for 00–09. A range starting at 10:00 never shows the bug.
- `mediawiki_history` lags pageviews by weeks, invisibly: the `2026-09` snapshot (generated 2026-10-05) has a `2026-10` file that's a 1.4MB stub covering only early October while pageviews are current to yesterday. `q2_spikes_news` reports three states, not a boolean — `NEWS_UNKNOWN` covers both this gap and the no-ITN-page case.
- **Q2's ±24h ITN match cannot say "no", so `NEWS_MATCHED` isn't evidence.** The ITN page is edited ~6.6x/day: on enwiki 2026-09-14..20 (136 edits, 46 in-window) **168/168 hours** sit within ±24h of some edit — `NEWS_ABSENT` is unreachable by arithmetic. Spikes' median distance to the nearest edit (2.45h) matches an arbitrary hour's (2.53h), so proximity carries no information. Base rates: ±12h 92.3%, ±6h 76.2%, ±3h 54.8%, ±1h 28.6%. Tightening the window narrows but doesn't fix this — the real test is matching the spiking article against what the ITN revision *links to*.
- `revision_dim` only knows pages *edited during the months downloaded*. Small wikis publish one all-time file (simplewiki: 605K pages, complete coverage); enwiki publishes monthly files and only fetches months the date range touches, so its revision half covers recently-edited pages only — don't read `avg_revisions` as a whole-wiki average. Coverage is also **correlated with the effect**: 3.0%/16.6%/23.7%/43.0% from `<1KB` to `20KB+`, so the charted 43.6x gradient is partly coverage. `avg()` skips nulls, putting `avg_revisions` (covered only) and `avg_views` (all articles) on different denominators in the same tooltip — zero-filled the gradient is 0.61 → 377.88.
- `mediawiki_history` dumps have no `-latest-` alias and only the last two monthly snapshots are retained — a hardcoded snapshot name goes stale within months, so `mediawiki_history.py::download` discovers the current snapshot and per-wiki filenames from the dumps site's own listings. Small wikis (e.g. simplewiki) publish one all-time `.tsv.bz2` file, not bigger wikis' monthly series — don't assume the monthly pattern unconditionally.
- Simple English Wikipedia has no actively-maintained "In the news" page — confirmed against the `simplewiki` dump, the only `Current_events`-titled pages are redirects. Q2's news correlation (`mediawiki_history.itn_page_title`) needs `enwiki`, not the default `simple` config, for real signal (see `docs/sources/wikinews-itn.md`).
